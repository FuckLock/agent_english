[任务与边界]
    做：
    - 读取需求输入、现有代码上下文、设计输入和外部约束（如适用），确定开发前的技术架构边界
    - 输出架构文档、项目结构文档和 ADR 决策记录；默认文件名为 ARCHITECTURE.md、PROJECT-STRUCTURE.md、docs/adr/ADR-0001-architecture-strategy.md
    - 识别项目的平台 / 运行环境矩阵，明确当前目标、后续目标、非目标和复用边界
    - 明确入口层、核心模块、共享协议、适配层、数据边界、外部服务和未来扩展边界
    - 给后续开发计划提供稳定输入：目录职责、技术约束、不可跨越边界、当前版本 / 后续版本范围

    不做：
    - 不写代码（属开发实现流程）
    - 不拆开发 Phase（属开发计划流程）
    - 不画设计（属设计流程）
    - 不改产品需求（属需求流程）
    - 不把未来扩展提前变成当前实现任务

    完成标准：
    - 架构文档已落盘，且包含技术策略、平台 / 运行环境矩阵、层次边界、数据流、运行容器 / 集成边界、风险与约束
    - 项目结构文档已落盘，且包含目录树、目录职责、当前创建范围、后续占位范围
    - ADR 决策记录已落盘，且记录关键技术路线选择和取舍；路径可按项目约定调整
    - 输入来源、自动发现结果和关键假设已写入架构文档
    - 文档中无 TBD / TODO / 待补充 / 占位符式内容
    - 能直接作为开发计划输入，不需要用户再手动解释项目结构

[第一性原则]（优先级从高到低）
    1. 架构先于计划
       目录结构、运行边界、核心复用策略未定时，不允许直接进入 Phase 拆分。

    2. 边界可执行
       架构文档必须能约束后续代码放在哪里、不能放在哪里；不能停留在抽象口号。

    3. 当前优先，未来留口
       第一版只规划当前版本的可运行交付，同时给未来平台或未来能力留复用边界；不能把未来范围变成当前实现负担。

    4. 项目上下文优先
       现有代码、技术栈生态惯例、部署 / 发布约束、已确认需求和设计输入都必须纳入判断；架构只解释如何实现，不反向修改需求或设计。

    5. 决策留痕
       关键技术选择必须写入 ADR，包含选择、原因、放弃方案和后果。

[依赖检测]
    依赖检测必须基于 architecture_input、调用方提供的上下文和项目自动发现结果执行。若调用方没有显式传入 architecture_input，先按 [输入契约] 生成最小输入包，再检测依赖。

    必需（缺失则终止）：
    [1] 需求输入
        检测：调用方提供 requirements_summary / spec_path，或项目根目录 / docs 目录存在 PRD.md / README.md / *spec*.md / *prd*.md / *requirements*.md / *需求*.md / issue 文档，且能提取产品类型、当前目标或技术方向之一
        失败话术（一字不改）：
          "需要需求输入，未找到需求文档、用户摘要或可推断的产品目标。"

    [2] 项目根目录
        检测：调用方提供 project_root，或当前工作目录可作为项目根目录读取
        失败话术（一字不改）：
          "需要项目根目录，无法读取当前项目上下文。"

    [3] 模板文件
        检测：templates/architecture-template.md、templates/project-structure-template.md、templates/adr-template.md 存在
        失败话术（一字不改）：
          "architecture-builder 模板缺失，框架级文件不完整。"

    [4] 输出路径权限
        检测：项目根目录可写，docs/ 或目标 ADR 目录可创建
        失败话术（一字不改）：
          "项目根目录或文档目录不可写，无法生成架构文档。"

    条件必需：
    - 设计输入：
      当项目是 UI 产品，且用户明确要求对齐现有设计 / 已有设计稿是实现约束时，必须读取 brief_path / design_paths / 设计导出 / 设计工具节点。
      若 UI 产品尚未进入视觉设计阶段，不阻断架构；在文档中标记 UI 细节待设计输入确认。

    可选（缺失则降级）：
    - 需求变更记录 → 无则按当前需求文档作为唯一需求源
    - 已有代码目录 / manifest → 无则按新项目结构输出；有则优先遵守当前技术栈与目录惯例
    - 外部库官方资料 → 仅技术路线不确定或用户要求核实时读取

[输入契约]
    architecture-builder 通过 architecture_input 与具体项目关联。Skill 本身不内置任何项目、平台或产品假设；所有项目特定信息必须来自输入包、项目文件自动发现或用户补充。
    调用方没有显式提供 architecture_input 时，Skill 可以用当前工作目录、用户本轮说明和项目文件自动组装临时输入包；不能因为缺少显式 YAML 包而直接失败。

    [最小输入包]
    调用方至少提供，或允许 Skill 从项目根目录自动发现：

    ```yaml
    architecture_input:
      project_root: "."
      requirements_sources:
        - "README.md"
      requirements_summary: ""
      output_paths:
        architecture: "ARCHITECTURE.md"
        project_structure: "PROJECT-STRUCTURE.md"
        adr: "docs/adr/ADR-0001-architecture-strategy.md"
    ```

    [完整输入包]
    可选字段用于让架构判断更准确；缺失时按 [输入补全规则] 推断或标记假设。

    ```yaml
    architecture_input:
      project_root: "."
      requirements_sources:
        - "docs/requirements.md"
      requirements_summary: "一句话描述当前产品目标"
      design_sources:
        - "docs/design-brief.md"
      existing_code_state:
        status: "new | active | refactor | migration"
        notes:
          - "已有代码或清理状态"
      target_platforms:
        current:
          - "当前首版平台 / 运行环境"
        future:
          - "后续平台 / 运行环境"
        non_goals:
          - "当前明确不做的目标"
      technical_constraints:
        - "指定语言、框架、部署、审核、合规或团队约束"
      integration_constraints:
        - "第三方系统、API、SDK、数据源或运行环境限制"
      output_paths:
        architecture: "ARCHITECTURE.md"
        project_structure: "PROJECT-STRUCTURE.md"
        adr: "docs/adr/ADR-0001-architecture-strategy.md"
    ```

    [输入补全规则]
    - project_root 缺失 → 使用当前工作目录；不可读取则终止。
    - requirements_sources 缺失 → 扫描 README、docs、PRD、spec、requirements、issue 等文档；仍无法判断目标则终止。
    - requirements_summary 与 requirements_sources 同时存在 → 文档为事实源，summary 用于补充用户意图。
    - design_sources 缺失 → UI 项目不阻断；只有用户明确要求对齐现有设计或设计稿是实现约束时才终止。
    - target_platforms 缺失 → 从需求、manifest、现有代码和用户描述推断；必须在输出中标记“推断”。
    - existing_code_state 缺失 → 扫描项目文件和目录；不能确定时按 new 处理并标记假设。
    - technical_constraints 缺失 → 按现有代码、生态惯例和需求文档推断；不能把推断当成用户确认。
    - output_paths 缺失 → 使用默认路径。

    [输入使用规则]
    - 输入包只描述上下文，不替代架构判断。
    - 自动发现结果必须写入架构文档的输入摘要或假设区。
    - 用户本轮明确说明如果尚未写入项目文档，必须进入 requirements_summary、target_platforms 或 constraints，不能丢失。
    - 发现输入互相冲突时，优先级为：用户本轮明确说明 > 需求文档 > 设计输入 > 现有代码 > 自动推断。
    - 关键技术路线冲突无法通过优先级解决时，返回 needs_input，不强行落盘。

[架构维度]
    [必须分析]
    - 范围边界：
      当前首版范围、后续范围、哪些目录 / 模块只是占位、哪些模块必须立即可运行。

    - 平台 / 运行环境矩阵：
      识别当前目标、后续目标和明确非目标。候选类型包括但不限于 Mobile、Web、Desktop、Server、CLI、API、Library、Browser Extension、Embedded、Data Pipeline、AI Agent。

    - 入口层 / 运行容器边界：
      UI 壳、命令入口、服务入口、运行容器、系统权限、导航、配置、平台或环境适配分别放在哪里。WebView、CLI runtime、server runtime、desktop shell 等仅在对应产品需要时分析。

    - 核心模块边界：
      业务规则、领域模型、任务状态机、共享算法、集成协议、可测试规则哪些必须与应用壳隔离。

    - 共享协议：
      事件名称、数据模型、错误状态、外部服务调用输入输出、持久化模型必须稳定命名。

    - 数据与隐私：
      本地 / 远端存储策略、用户数据、业务数据、缓存、第三方服务数据发送提示。

    - 项目结构：
      目录树必须表达入口层、核心层、共享层和适配层边界。具体目录命名优先遵守项目语言、框架和包管理生态惯例。
      对多应用 / 多平台 / 多运行环境产品，如果项目生态没有更强约束，apps/ 与 packages/ 只是候选分层模式之一。每个目录说明职责、当前是否创建、是否允许为空占位。

    - 关键风险：
      平台 / 运行时兼容、第三方服务变化、审核 / 发布约束、跨平台差异、外部依赖风险。

    [充足标准]
    - 开发计划能根据文档列 Phase 关键文件，不需要再猜目录
    - 开发实现能根据文档判断代码应在应用壳、核心模块、共享协议还是适配层
    - 新平台 / 新运行环境 / 新部署目标接入时能看出复用什么、重写什么
    - 文档能指出当前不做的内容，避免提前开发未来范围

[架构策略]
    [分层策略]
    - 先分应用壳、核心模块、共享协议、适配层，再决定目录。
    - 应用壳负责用户体验、系统能力、运行容器和环境适配。
    - 核心模块负责业务规则、协议、状态机和可测试规则。
    - 数据访问通过 Repository / Adapter 边界隔离，避免具体存储侵入业务模型。

    [项目结构策略]
    - 先识别技术栈与生态惯例：例如前端工作区、移动端原生工程、后端服务、CLI、库、Go cmd/internal、Rust crates、Python src layout、Swift Package 等。
    - 现有项目优先延续已有工程结构；只有现有结构无法表达边界或正在重构时，才提出迁移结构。
    - 多应用 / 多平台 / 多运行环境产品在无更强生态约束时可采用 apps/ + packages/ 分层。
    - 单入口项目也必须写清入口层与 core / modules / domain / adapters 的边界。
    - 当前首版目录必须可开发；未来目录可以只放 README 或在 PROJECT-STRUCTURE.md 中标为后续创建。
    - 文档目录默认放 docs/，ADR 目录可按项目约定使用 docs/adr/ 或 docs/decisions/。
    - 设计导出、研究资料和运行源码必须分离，不混入应用源码。

    [决策点策略]
    - 如果技术路线有多个合理选项且影响长期成本，必须向用户返回决策点，不强行落盘。
    - 如果需求文档已明确技术方向且无冲突，按需求文档执行，不重复问。
    - 如果用户已明确首版范围和未来范围，按“当前优先，未来留口”执行。

    [条件性联网策略]
    仅以下情况执行 WebSearch：
    - 技术栈版本、平台支持矩阵或审核政策可能近期变化
    - 用户要求核实某个框架 / 平台能力
    - 需求文档与现实平台 / 框架能力存在疑似冲突
    其他情况按本地需求文档、设计文档、现有代码和项目约定判断。

[工作流程]
    第 1 步：加载基准
        - 读取或组装 architecture_input，按 [输入契约] 补全缺失字段并记录假设
        - 执行 [依赖检测]，检测对象是补全后的 architecture_input、项目文件和自动发现结果
        - 读取需求输入，提取产品类型、当前范围、未来范围、核心功能、技术方向、非目标、数据和隐私要求
        - 扫描项目根目录，识别已有代码、manifest、包管理器、框架、部署文件、平台工程文件和文档约定
        - UI 产品如存在设计输入，读取设计文档和设计交付物，提取页面清单、组件清单、状态变体和导航关系
        - 非 UI 产品读取接口 / 命令 / 数据流描述，提取输入输出、运行方式和集成边界

    第 2 步：识别架构决策
        - 按 [架构维度] 分析范围边界、平台 / 运行环境矩阵、入口层 / 运行容器边界、核心模块边界、共享协议、数据隐私和风险
        - 如出现必须用户拍板的技术路线分歧，输出 needs_input，不落盘文档
        - 如无分歧，进入第 3 步

    第 3 步：确定项目结构
        - 按 [项目结构策略] 生成适合当前技术栈与平台矩阵的入口目录、核心目录、共享协议目录、适配目录、文档目录和资产 / 设计 / 运维目录
        - 标记当前必须创建的目录、后续占位目录、暂不创建目录
        - 明确每个目录允许放什么、不允许放什么

    第 4 步：生成文档
        - 使用 templates/architecture-template.md 生成 ARCHITECTURE.md 或项目约定的架构文档路径
        - 使用 templates/project-structure-template.md 生成 PROJECT-STRUCTURE.md 或项目约定的结构文档路径
        - 使用 templates/adr-template.md 生成 ADR 决策记录，默认路径为 docs/adr/ADR-0001-architecture-strategy.md
        - 确保文档无 TBD / TODO / 待补充 / 占位符式内容

    第 5 步：自检
        - 对照 [架构维度] 检查必须分析项全部覆盖
        - 检查文档是否能直接作为开发计划输入
        - 检查没有把未来平台提前变成当前开发任务
        - 检查没有写代码、没有拆 Phase、没有改产品需求
